\doxysubsection{Detailed Description}
Basic \mbox{\hyperlink{class_lambda___klencki}{Lambda\+\_\+\+Klencki}} class. The \mbox{\hyperlink{class_lambda}{Lambda}} fit comes from Appendix A in Klencki+21 (\href{https://ui.adsabs.harvard.edu/abs/2021A\%26A...645A..54K/abstract}{\texttt{ https\+://ui.\+adsabs.\+harvard.\+edu/abs/2021\+A\%26\+A...\+645\+A..\+54\+K/abstract}}). \mbox{\hyperlink{class_lambda}{Lambda}} is thus estimates as\+: log10(lambda) = a$\ast$x$^\wedge$3 + b$\ast$x$^\wedge$2 + c$\ast$x + d where x=log10(\+R) The value of a,b,c,d depends on the \mbox{\hyperlink{class_mass}{Mass}} (Mzams), Z (metallicity) and \mbox{\hyperlink{class_radius}{Radius}}. All these values are tabulated for a set of given tracks, the table is in auxiliary\+\_\+data/lambda\+\_\+fit\+\_\+\+Klencki21.\+dat (original link https\+: //ftp.science.\+ru.\+nl/astro/jklencki/).

During the first class initialisation in each thread, the table is loaded as a static 2D vector The following class initialisations will just use the already loaded table.

The lambda can be retrieved using the overload operator (\mbox{\hyperlink{class_star}{Star}} $\ast$s) or (double Mzams, double Z, double R).

Notice\+: the lambda is estimated by Klenci+21 using MESA tracks between 10 and 80 Msun and Z/\+Zsun 0.\+01 -\/ 0.\+1, where Zsun=0.\+017 (not all the tracks contains all the ranges in Z). Using this class the lambda is estimated in a quantised way, i.\+e. for a Mzams and a Z not present in the table, the closed track with Mtrack\texorpdfstring{$>$}{>}Mzams and Ztrack\texorpdfstring{$>$}{>}Z. If Mzams\texorpdfstring{$<$}{<}10, Mtracks=10 is used, for Z/\+Zsun\texorpdfstring{$<$}{<}0.\+01, Z/\+Zsun=0.\+01 is used.

Here now we define two quantities that are used to load the external table only once per class per thread. In this way we can save memory not loading one table for each \mbox{\hyperlink{class_lambda}{Lambda}} instance, this is possibile using static variables. At the same time using thread\+\_\+local we force to have one separate definition for these variable for each thread avoiding data racing. In this case it is equivalent to defining the variable as threadprivate (see \href{https://stackoverflow.com/questions/60932116/does-thread-local-work-for-openmp-threads}{\texttt{ https\+://stackoverflow.\+com/questions/60932116/does-\/thread-\/local-\/work-\/for-\/openmp-\/threads}}), Variables that appear in threadprivate directives or variables with the \+\_\+\+Thread\+\_\+local (in C) or thread\+\_\+local (in C++) storage-\/class specifier are threadprivate
